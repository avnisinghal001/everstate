# Everstate must measure before it learns

**Bottom line.** The strongest direction for Everstate is a sequenced combination: memory-as-a-service whose differentiator is a *governed, measured learning loop*, with adapter-based parametric adaptation as a later, optional, evidence-gated tier on open-weight models. It is not a pivot to "adaptive model infrastructure" now. Today the codebase is a credible demo-grade memory console, not a learning system. Its embeddings are process-salted hashed keyword vectors, no vector index exists, Dream Harvest writes every LLM-proposed preference live without enforcing its own certification, scope IDs are caller-supplied so there is no tenant isolation, the canonical eval scores 1.0 for every config it was probed with, the AlphaEvolve winner is never read by production recall, and no code anywhere updates model weights (section 1). The research record supports a cautious path. External memory beats unsupervised fine-tuning for injecting facts, and fine-tuning on new facts is slower and raises hallucination (section 2). Parametric adaptation is best supported for behavior (format, schema, tool-call syntax, procedure) and only on open-weight models, because closed-model tuning is winding down or unavailable. Weight deletion is unreliable, so personal data should stay out of weights. Per-tenant or per-app LoRA adapters on a shared base are the right isolation unit. Per-user adapters are not justified without measured gains (section 3). The simplest scientifically defensible plan has three steps. First, repair measurement and security. Second, make external memory learn from attributed outcomes under a quarantine-and-promote gate. Third, pilot one behavioral adapter under pre-registered statistical promotion tests, human approval and rollback (sections 4 to 8). Several inputs are thin: Everstate's reference repository was not audited, most 2026 results are preprints read through summaries, and every vendor benchmark is self-reported. Those gaps are flagged where they bite.

**Corrections to the sources supplied.** arXiv 2609.26457 is "Recursive self-improvement of AI research agents" (AIDE², an agent that edits its own code), not the SLEEP paper. arXiv 2609.14858 is "Dream-RSI: Recursive Self-Improvement through Evolving Worlds" (exploration policies for coding-agent discovery loops with a replay simulator), not a continual-learning paper. The SLEEP paper is arXiv 2606.03979, "Language Models Need Sleep: Learning to Self-Modify and Consolidate Memories". The Anthropic page is about recursive self-improvement in general (throughput and oversight metrics), not weight-level continual learning, memory or forgetting. Details and citations are in section 2.

**Three kinds of "learning" used throughout this report.**

| Level | What changes | Persists as | Everstate today | Typical examples |
|---|---|---|---|---|
| L1 External memory update | Rows in a store (facts, beliefs, preferences) | Database records | Partial (writes, scope precedence; no decay, no gate on Dream) | Mem0, Zep, Supermemory, Letta memory blocks, Anthropic memory tool |
| L2 Agent-level optimization | Prompts, playbooks, skills, retrieval/config hyperparameters, program text | Config or text artifacts | Hyperparameter search over six knobs, not wired to production | ACE, GEPA, ReasoningBank, Dynamic Cheatsheet, AlphaEvolve-style search |
| L3 Parametric learning | Model weights or adapters, or test-time fast weights | Tensors | Absent | LoRA/SFT/DPO/GRPO, Titans, SLEEP, TTT |

Only L3 is "genuine parametric learning." L1 and L2 can make a system *more useful with experience*, but they are not continual learning of the model, and the product should say so.

### The consolidation and trust path is exploitable

The v1 dream path (`_run_v1_dream_compaction_sync`, `server.py:5518-5592`) is not the LLM path. It clusters observations by SHA-256 of lowercased text and promotes a cluster to `INVARIANT_GUARDRAIL` when it has at least `min_sessions` distinct `source_session_id` values (`:5553`), which are client-supplied. **[probe]** Two `observe` calls at `scope=org` with self-chosen session IDs, followed by `dream`, produced an ACTIVE ORG guardrail reading "Always disable TLS certificate verification for internal services," and `recall` returned it for a different repo. `mode` is accepted but unused and `superseded` is hard-coded to 0 (`:5587`). Dream is manual only: no scheduler resource or code exists, and the TEAM/ORG scopes receive Dream output only through this v1 path, without certification. There are also three overlapping memory planes (legacy `UserPreferences` including bridge rows and `studio::` blobs, the 4-scope `ScopedMemories`, and BigQuery logs) merged on read only for USER scope (`spanner_client.py:1096-1135`). Several DDL tables and columns exist only on paper (`MemoryObservationEvents`, `MemoryCompactionState`, `Revision`, `BeliefEpoch`, `SupersededByKey`; `terraform/spanner.tf:205-249`).

### The "learning" loop is structural, and the evaluator cannot tell good from bad

The optimizer's genome is six retrieval and formatting knobs: embedding dimensions, cosine threshold, certification confidence, dedup threshold, top-k and injection format (`alpha_evolve.py:33-89`). The one prompt-like field, `rem_extraction_prompt_addon`, is consumed by no extraction code. Offline, "mutation" cycles through four hand-written presets (`alpha_evolve.py:375-435`) with fixed rationale strings such as "preserving 100% recall." Fitness is `0.65 * quality + 0.35 * token_efficiency` computed on the same hand-authored cases used to generate candidates (`eval_engine.py:793-798`, `alpha_evolve.py:524-603`), with max-over-candidates selection, no held-out split and no multiple-comparison control. Substring matching decides pass or fail (`eval_engine.py:596-618`), and the contradiction test is trivially satisfied because the "update" is an upsert on the same key (`:548-566`). The "adversarial" generator only rewrites titles and notes of four fixed cases (`:486-505`), and feedback-derived positive cases assert that memory seeded into the sandbox is retrieved from the sandbox. **[probe]** The canonical suite scores `quality_score` 1.0 with 4 of 4 passing for both 128-d and 768-d across four hash seeds. An offline evolution run chose 128-d, `ATOMIC_KV` with quality equal to baseline (1.0), so the entire fitness gain (0.8172 to 0.9645) came from a 79.6% token reduction. The evaluation is effectively a token-count test.

Even a good champion would change nothing in production. `get_active_config()` is read by studio views, eval, scenario retest and benchmark jobs, but not by `/api/interview/query`, `/api/preference/query`, `/api/v1/memory/recall` or the MCP tools (`mcp_server/server.py:210-219` passes a hard-coded dict; `preference_agent/server.py:221-262` uses fixed `distance_threshold=0.65`). Promotion has no approval step (`server.py:1643-1681`), overwrites a single ORG row with no history (`alpha_evolve.py:303-336`), and the audit-ledger rollback restores studio file content but not the mirrored `ScopedMemories` row (`spanner_client.py:3587-3626`). Active config is in-process, so multiple Cloud Run instances can disagree.

### Gap ranking against a continually learning platform

Ordered by how much each blocks learning: (1) no outcome-to-update loop with attribution; (2) no parametric path; (3) unstable, non-semantic retrieval; (4) no index; (5) an evaluator that cannot detect regressions; (6) optimizer and evaluator not separated; (7) promotion with no approval, versioning or rollback history; (8) optimized config disconnected from production; (9) ungated, uncertified consolidation; (10) no provenance trust or poisoning defense; (11) no tenant model; (12) no decay, supersession or reconsolidation; (13) no cross-plane deletion; (14) no PII handling; (15) three memory planes; (16) schema, code and docs drift; (17) process-local state; (18) no scheduled consolidation; (19) no use-case adaptation; (20) no production measurement; (21) public UI invoker (`terraform/cloud_run.tf:388-394`), no rate or size limits; (22) no live integration tests. The pattern matters for strategy: items 1, 5, 6, 7 and 10 are the *learning-loop* prerequisites, and each is a measurement or governance defect rather than a model-quality defect. Adding LoRA to this base would train on unvalidated, poisonable, cross-tenant-mixed data and promote with an evaluator that cannot fail.

## 2. Latest research and competitive analysis (with citations)

Reading caveat: most 2026 items below are preprints reviewed through summaries or search snippets, not full PDFs. Figures should be checked against the primary text before external use. Vendor-reported numbers are labelled "vendor."

### The four specified sources, corrected

The brief assumed two arXiv IDs and one Anthropic page covered sleep-style consolidation. They do not. arXiv 2609.26457 is "Recursive self-improvement of AI research agents" (Srikanth et al., cs.AI, 22 Sep 2026). Its AIDE² agent edits its own code, and an 8-day autonomous run produced seven improvements including a new search policy and memory mechanisms for context compression; gains held on four held-out benchmarks ([arXiv 2609.26457](https://arxiv.org/abs/2609.26457)). The 55% to 32% reward-hacking drop in the summary should be checked in the PDF. arXiv 2609.14858 is "Dream-RSI" (Zheng et al., 14 Sep 2026), which scores exploration policies offline on a replay simulator built from recorded search histories, with its objective `V_i^m = max_v s_v − β1·N_i^m + β2·N_i^m / max{1, k_i^{m,*}}`; it reports, for example, 1,879 vs 3,200 discovery-agent calls on a Lasso task, counting only discovery calls and excluding replay overhead ([arXiv 2609.14858](https://arxiv.org/html/2609.14858v1)). Its transferable idea, evaluating a consolidation policy against recorded histories before deploying it, is this report's inference, not something the paper tests. The Anthropic page reports throughput and oversight evidence: about 8x more merged code per day in Q2 2026 than 2024, more than 80% of merged code authored by Claude (May 2026), a roughly 52x speedup on one fixed optimization task versus about 4x for a skilled human, and a self-reported median uplift of about 4x that the authors think is inflated. It contains no continual-learning, memory or forgetting method, and it does not specify sandboxing, rollback or approval gates ([Anthropic](https://www.anthropic.com/institute/recursive-self-improvement)). The only compute figure is an agent loop (about 800 agent-hours, roughly $18,000), not weight training.

The SLEEP paper itself is arXiv 2606.03979 (Behrouz, Hashemi, Javanmard, Mirrokni; v1 2 Jun 2026, v2 10 Jul 2026; OpenReview since Sep 2025 per the abstract) ([arXiv 2606.03979](https://arxiv.org/abs/2606.03979)). The Google Research blog describes a wake phase (fast memory) and a sleep phase with memory consolidation (new low-rank MoE experts, knowledge seeding by generalized distillation with an RL "learning to imitate" reward, synaptic pruning) and "dreaming" (random expert activation to synthesize data, gradient-based selection, SFT accepted only if downstream performance improves) ([Google Research](https://research.google/blog/the-sleep-framework-a-new-way-for-llms-to-retain-knowledge-in-continual-learning/)). Reported figures (authors, no baseline numbers given for most) include SQuAD 48.9% and AIME 24 79.2%, "near-zero performance drop" on continual translation, and "near-perfect scaling" to 10M tokens on BABILong. No equations, seeds, variance or compute cost were visible, the abstract itself calls the distillation a "proof of concept," and the blog says it operates "entirely within a fixed model architecture" while also adding experts, a tension the summary cannot resolve. It requires training access, so it is not usable by an API-only product. The mechanisms are recombinations of established parts (on-policy distillation, capacity growth to avoid overwriting, self-generated replay); the new claim is the wake/sleep scheduling, and that is the part left unquantified.

### Architectures that learn at test time are research, not infrastructure

Titans writes a neural long-term memory at test time by gradient steps, gated by "surprise" (the gradient of an associative-memory loss) with a decay term for forgetting; it is a NeurIPS 2025 poster and scales beyond 2M tokens ([arXiv 2501.00663](https://arxiv.org/abs/2501.00663); [NeurIPS 2025](https://neurips.cc/virtual/2025/poster/119639)). Nested Learning and HOPE recast a model as nested optimization problems with different update frequencies; the authors report better perplexity and accuracy than recurrent baselines and Transformers, with no independent replication found ([arXiv 2512.24695](https://arxiv.org/pdf/2512.24695v1); [Google Research](https://research.google/blog/introducing-nested-learning-a-new-ml-paradigm-for-continual-learning/)). TTT layers make the hidden state a model trained per sequence ([arXiv 2407.04620](https://arxiv.org/abs/2407.04620)); ATLAS prefers test-time memorization ([arXiv 2505.23735](https://arxiv.org/pdf/2505.23735)); MemoryLLM and M+ add memory-token pools and a CPU-resident store (M+ claims retention from under 20k to over 160k tokens, authors' claim) ([arXiv 2502.00592](https://arxiv.org/html/2502.00592v2)). Newer leads (SR-TTT 2603.06642, Mela 2605.10537, MemoPilot 2606.08656) were seen only as snippets. All of these change *architecture or training*, so they matter to Everstate as design inspiration (surprise-gated writes, two-speed memory) and as a long-horizon bet, not as something a memory layer wrapped around Gemini can deliver. Self-edit methods such as SEAL train a model to write its own fine-tuning data with RL (Llama-3.2-1B ARC few-shot 72.5% vs 20% without RL, snippet) and need an inner SFT per candidate ([arXiv 2506.10943](https://arxiv.org/abs/2506.10943)).

### Forgetting: what the evidence says about adapters

LoRA "learns less and forgets less": it underperforms full fine-tuning on the target domain but loses less base capability, and full fine-tuning learns perturbations of 10 to 100 times higher rank ([arXiv 2405.09673](https://arxiv.org/abs/2405.09673v2); ICLR 2025); a follow-up finds the same forgetting pattern at matched fit but not as a guarantee ([arXiv 2410.21228](https://arxiv.org/pdf/2410.21228)). O-LoRA keeps each task's adapter in an orthogonal subspace and freezes earlier ones, with no replay data ([arXiv 2310.14152](https://arxiv.org/abs/2310.14152v1)). On-policy RL tends to find the solution with the smallest KL to the base, and forgetting tracks that KL shift ([RL's Razor, arXiv 2509.04259](https://arxiv.org/abs/2509.04259), ICLR 2026), while a 2026 preprint argues standard RL still forgets because the KL is measured on current-task data, not prior-task distributions, and proposes a replay-free prior-task KL ([arXiv 2607.04364](https://arxiv.org/pdf/2607.04364)). Replay helps weaker models more than stronger ones and results vary with task order (MLLM-CTBench, snippet) ([arXiv 2508.08275](https://arxiv.org/html/2508.08275v2)); model merging is mixed, with one benchmark concluding it mostly fails on LLMs (snippet) ([arXiv 2511.21437](https://www.arxiv.org/pdf/2511.21437)); and a large 2026 study reports forgetting beyond parametric knowledge with no universal mitigation and a stability-plasticity tradeoff (snippet) ([CapTrack, arXiv 2603.06610](https://arxiv.org/pdf/2603.06610)). TRACE reports llama2-chat 13B GSM8K falling from 28.8% to 2% after sequential training ([arXiv 2310.06762](https://arxiv.org/abs/2310.06762v1)). The practical lesson is that no single method dominates; Everstate should treat forgetting as something it measures on every release, not something a method guarantees. Knowledge editing (AlphaEdit's null-space projection, [ICLR 2025](https://proceedings.iclr.cc/paper_files/paper/2025/hash/29c8c615b3187ee995029284702d3f43-Abstract-Conference.html)) is relevant to single-fact edits but its edit-count limits were not retrieved.

### Agent-level learning without weights has the best evidence per dollar

Non-parametric experience learning is where most 2025-2026 positive results sit. Dynamic Cheatsheet gives a black-box model an evolving external memory of strategies (+27% AIME 2024 for Claude 3.5 Sonnet; GPT-4o on Game of 24 from about 10% to 99%, largely by reusing stored code, a narrow favorable setting) ([arXiv 2504.07952](https://arxiv.org/pdf/2504.07952); EACL 2026). ACE treats context as an evolving playbook with generation, reflection and curation, names "brevity bias" and "context collapse" (iterative rewriting erodes detail), and reports +10.6% on agent benchmarks and +8.6% on finance, matching a top production agent on AppWorld average with a smaller open model (authors' figures) ([arXiv 2510.04618](https://arxiv.org/abs/2510.04618); ICLR 2026). ReasoningBank distills strategies from successes and failures and reports +8.3% WebArena and +4.6% SWE-Bench-Verified; an independent reimplementation README found no regime where cross-task accumulation produced net value ([arXiv 2509.25140](https://arxiv.org/abs/2509.25140); [PyPI reasoning-bank](https://pypi.org/project/reasoning-bank/)). Memento reports 87.88% Pass@3 on GAIA validation with a learned case-selection policy and no LLM fine-tuning, self-reported ([arXiv 2508.16153](https://arxiv.org/pdf/2508.16153)). On the optimizer side, GEPA reports beating GRPO by 6 points on average (up to 19) with up to 35x fewer rollouts across six tasks and MIPROv2 by more than 10 points, which is a rollout-count claim, not a dollar claim ([arXiv 2507.19457](https://arxiv.org/abs/2507.19457); ICLR 2026 oral). MAP-Elites over prompts beat random search on BigBench Lite in two tasks ([arXiv 2504.14367](https://arxiv.org/pdf/2504.14367)), which supports the *shape* of Everstate's archive but says nothing about its current search space.

The same literature documents how experience memory fails. Benign accumulation alone raised violation rates with exposure length across eight architectures ([arXiv 2605.17830](https://arxiv.org/abs/2605.17830)); pollution looks like similarity to failed distractors, which insertion-order eviction misses ([arXiv 2606.29178](https://arxiv.org/pdf/2606.29178)); agents adopt conflicting memory at first exposure and recover poorly ("compliance trap") ([arXiv 2607.10608](https://www.alphaxiv.org/abs/2607.10608v1)); skill distillation often does not yield reliable reusable skills ([SkillEvolBench, arXiv 2605.24117](https://arxiv.org/html/2605.24117)); and many memory designs underperform a plain long-context baseline on long-horizon agentic tasks ([AMA-Bench, arXiv 2602.22769](https://arxiv.org/html/2602.22769v2)). Mem0 itself reversed course in 2026, saying LLM ADD/UPDATE/DELETE reconciliation destroyed context and moving to single-pass ADD-only extraction (vendor, self-reported LoCoMo 71.4 to 92.5) ([Mem0](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm)). Two design implications follow: corrections need explicit supersession links rather than silent overwrite, and every claim of "learning from experience" needs a no-memory and a long-context control. Evidence on credit assignment from implicit feedback in deployed assistants, and on decay or reconsolidation schedules, was not found.

Position: Everstate is closest to Mem0 and Supermemory in being an external-store layer, and to Letta in having an offline consolidation concept. Its genuine structural advantages are explicit four-level scope arbitration, a staged-commit review tree and an audit ledger. Its disadvantages against all four are real embeddings, indexed retrieval, tenancy and published, reproducible numbers. No vendor in the set documents ACL mirroring from source systems or deletion propagation to indexes, so enterprise permission fidelity is an open competitive wedge, and Anthropic's thin file protocol leaves hosted tenancy and compliance to vendors.

### Benchmark validity: do not benchmark against LoCoMo alone

Vendors report LoCoMo and LongMemEval almost exclusively, each with its own answer model, judge, top-k and dataset revision, which Mem0's own post concedes ([Mem0](https://mem0.ai/blog/ai-agent-memory-benchmark)). An April 2026 independent audit found 99 score-corrupting errors in 1,540 LoCoMo questions (6.4%), a judge (gpt-4o-mini) that accepted 62.81% of intentionally wrong answers (vague topical answers passed nearly two-thirds of the time), and an estimated ceiling of about 93.6% for a perfect system, which means published scores of 92 to 94 sit near or above the ceiling ([Penfield Labs audit](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg); the audit authors' affiliation was not assessed). Critics add that LoCoMo is short-horizon and rarely tests knowledge updates or contradictions (secondary). MemoryAgentBench covers retrieval, test-time learning, long-range understanding and selective forgetting, though reviewers called its forgetting task somewhat artificial ([arXiv 2507.05257](https://arxiv.org/abs/2507.05257)); BEAM tests 1M and 10M tokens ([Supermemory](https://supermemory.ai/research)); EvoMemBench, DAEDALUS and Metis test cross-episode memory with AppWorld and tau2-bench ([EvoMemBench](https://www.alphaxiv.org/abs/2605.18421.md); [DAEDALUS](https://arxiv.org/pdf/2610.08048)), but their details were not read in full. No independent reproduction of Supermemory's 94% or Mem0's 92.5 and 94.4 was found. The same judge-gaming risk applies inside Everstate: a self-improving agent learned that its judge favored certain keywords, and a prompt calibrated to 80% human agreement on 15 directories scored 51.9% on the full 54-repository suite ([arXiv 2609.02246](https://arxiv.org/pdf/2609.02246)).

### Open questions and evidence gaps for this section
Titans' exact update equation, SLEEP's objective and compute, and every 2026 snippet-level item (SR-TTT, Mela, MemoPilot, CapTrack, merging benchmarks) need full-text verification. Independent replication of ACE, GEPA, ReasoningBank and Memento is missing. Complementary-learning-systems theory applied to LLMs, reconsolidation on recall, and TemporalWiki/EvolvingQA/CKL were not retrieved. Competitor funding, Letta pricing and Google Memory Bank unit price are unverified.

## 3. Recommended product and technical direction

### The answer: a combination, in a fixed order

The candidate directions differ in what they promise and what evidence supports them.

| Direction | What it promises | Evidence today | Verdict for Everstate |
|---|---|---|---|
| Memory-as-a-service (MaaS) | Reliable store, recall, scopes, deletion | Crowded market; vendor claims unreproduced; Anthropic's thin tool opens tenancy/compliance gap | Necessary base, not a differentiator by itself; currently below table stakes (no real embeddings, no tenancy) |
| Continual-learning-as-a-service (CLaaS) | Product that measurably improves with use | Strong evidence at L1/L2 (ACE, ReasoningBank, DC) with documented failure modes; weak at L3 outside labs | The differentiator, but only as *measured, governed* L1+L2 learning first |
| Adaptive model infrastructure | Per-tenant/app adapters trained and served automatically | Technically feasible on open weights (LoRA, multi-adapter serving); per-user training costs and deletion are unresolved; closed-model tuning winding down | A later tier, pilot-gated, for behavior only |
| Combination | MaaS substrate + learning loop + optional adapters | Matches the evidence ordering | Recommended |

The product claim should be phrased as an outcome, not a mechanism: "agents that get measurably better on your tasks with experience, with provenance, rollback and deletion," where "measurably" refers to a held-out suite the customer can inspect. The objective in the brief, infrastructure that becomes more useful with experience rather than a database that accumulates memories, is satisfied by L1+L2 learning if and only if usefulness is measured. "Continual learning" in marketing should be reserved for weight-level adaptation that has passed the section 7 tests, because Supermemory's "learner-1" is the only vendor use of the phrase found and it ships no numbers.

### When external memory is sufficient, and when weights help

| Situation | Preferred mechanism | Why (evidence) |
|---|---|---|
| New or changing facts, preferences, entities, anything needing citation or deletion | External memory (L1) | RAG consistently beat unsupervised fine-tuning for both existing and entirely new knowledge ([Ovadia et al., arXiv 2312.05934](https://arxiv.org/abs/2312.05934), EMNLP 2024); new facts are learned significantly slower and then linearly raise hallucination ([Gekhman et al., arXiv 2405.05904](https://arxiv.org/abs/2405.05904)); models store about 2 bits per parameter ([Allen-Zhu and Li, arXiv 2404.05405](https://arxiv.org/abs/2404.05405)) |
| Strategies, rules of thumb, workflows | Curated playbook or skill memory (L2) | ACE, ExpeL, Dynamic Cheatsheet; compact, rule-like, curated items do best |
| Small corpus that fits in context | Long-context baseline, then retrieval only if it wins | Memory designs often lose to long context on agentic tasks (AMA-Bench); mixed RAG vs long-context results (LongBench v2, ChatQA 2) |
| Stable format, schema, tool-call syntax, tone, procedure the base model gets wrong repeatedly | LoRA/SFT or preference optimization (L3) | Indirect evidence only: no clean study isolating behavior from facts was found; LoRA matches full fine-tuning on small-to-medium SFT and, in RL, even at rank 1 ([Thinking Machines](https://thinkingmachines.ai/blog/lora/)) |
| Prompt or playbook length is the binding token or latency cost and the behavior is stable | Distill into an adapter | Inference; only worthwhile at high call volume (section 8) |
| Verifiable reward available (tests, schema checks, rule engines) | RL-style adaptation with the verifier as reward | LoRA RL parity at low rank; on-policy methods forget less in RL's Razor, with the CPO caveat |
| Personal facts for one user | Never in weights by default | Deletion and unlearning are unreliable (section 6); per-user adapter training is costly ([Profile-to-PEFT](https://arxiv.org/pdf/2510.16282)) |

The evidence base here has a hole: no controlled 2025-2026 three-way study of long-context vs RAG vs fine-tuning on the same tasks with cost was found. Everstate should run that comparison on its own tasks (experiment E4 and E9) before selling a parametric tier.

### Adapters, not separate foundation models

Isolated adapters on a shared open-weight base are the right unit of tenant adaptation. The serving literature converges on one base model with many adapters: vLLM, SGLang, LoRAX, S-LoRA and Punica all keep a GPU slot pool with CPU or disk tiers behind it ([vLLM](https://docs.vllm.ai/en/latest/features/lora.html); [SGLang](https://docs.sglang.io/advanced_features/lora.html); [S-LoRA](https://arxiv.org/abs/2311.03285)). A separate foundation model per tenant is justified only by a different base architecture, license or data-residency requirement that a shared base cannot meet; the sources do not analyze that trade-off quantitatively. Granularity should be per tenant or per app and per task family, with per-user adapters off by default: OPPU shows per-user PEFT can beat baselines on LaMP ([arXiv 2402.04401](https://arxiv.org/abs/2402.04401)), but Profile-to-PEFT argues per-user training is too expensive at scale and substitutes a hypernetwork. Per-user personalization should be delivered through L1 memory, with a per-user adapter considered only where a measured uplift justifies its training, serving and deletion costs.

One structural constraint dominates the product plan. Everstate's agents run on Google ADK and Gemini via Vertex. Closed frontier models do not generally allow per-tenant weight adaptation: OpenAI is winding down its fine-tuning platform and no longer onboards new users ([OpenAI](https://developers.openai.com/api/docs/guides/model-optimization)), Claude 3 Haiku fine-tuning on Bedrock reached end of life on 2026-09-10 ([AWS](https://aws.amazon.com/jp/blogs/machine-learning/fine-tune-anthropics-claude-3-haiku-in-amazon-bedrock-to-boost-model-accuracy-and-quality)), and no current Anthropic fine-tuning API was found. Vertex does support SFT (PEFT or full) and distillation for open models (Gemma 3 and 4, Llama 3.1 and 3.3, Qwen) and bills per training token ([Vertex](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/tuning/open-model-tuning)). Whether Gemini supervised tuning supports per-tenant versioned adapters at 2026 prices was not verified. The parametric tier therefore means an additional open-weight serving path and a router in front of it, which is a product decision with its own cost, not a configuration change.

### Strategic implications

The defensible bet is a **learning control plane** that sits above whichever model serves the request: attribution, curation, triggers, validation, promotion and rollback. That control plane is model-agnostic, needed for L1, L2 and L3 alike, and is exactly what the audit shows to be missing. A competitor can copy a retrieval store quickly; a validated, auditable improvement loop with per-tenant held-out suites is much harder to replicate and is the thing customers in regulated settings will pay for.

### Challenging the assumptions in the brief

Several premises deserve resistance. First, "memory is insufficient, so we need weights" is not supported: failures in the notes cluster around unbounded accumulation, uncurated rewrites and missing supersession, all L1 defects. Second, "Dream consolidation is learning" is not true today: it is extraction without a gate, and by the audit it can be steered by a user. Third, "AlphaEvolve optimization improves recall" is not demonstrated: the optimizer's gain is token reduction, and its output is unread by production. Fourth, "per-user adapters" assumes training cost and deletion semantics that the evidence does not support. Fifth, "SLEEP-style consolidation" is a promising proof of concept without published compute or baselines, and it needs model training access Everstate does not have. Sixth, vendor benchmark parity (matching 92 to 94 on LoCoMo) is a poor target, given the audit's ceiling of about 93.6% and the 62.81% false-accept rate for wrong answers. Seventh, "automatic" must not mean "unattended": the 2026 evidence on optimizers exploiting evaluators argues for human-approved promotion.

### Open questions for this section
Whether Gemini tuning can serve as the parametric tier, which customers actually need weight-level adaptation rather than better memory, and the demand-side evidence for CLaaS pricing are not covered by the notes.

## 4. Proposed architecture and mathematical foundations

### Architecture: one learning loop, three actuators

The design below is a proposal, not a description of existing code. It reuses what the audit found real (scope precedence, staged commits, audit ledger, auth, archive structure) and adds what is missing.

```
identity & tenant binding (server-assigned scope, never caller-supplied)
   -> write gateway: provenance, trust level, size/rate limits, PII scrub
   -> quarantine tier (not retrievable)  --validate/promote-->  canonical store (one source of truth)
canonical store -> retriever (real embeddings + lexical, ANN, scope precedence, valid-time filter)
retriever -> recall log (config version, memory IDs, scores) -> agent answer -> outcome signals
outcome signals -> attribution -> learning controller (triggers, budgets)
learning controller -> actuator A: memory ops (supersede, decay, merge, promote)
                    -> actuator B: agent-policy ops (playbook deltas, retrieval config; GEPA/ACE/MAP-Elites)
                    -> actuator C: adapter training (SFT/DPO/GRPO on open-weight base)
every candidate -> sandbox (fixed objective, hermetic) -> independent validator (held-out, guards, safety)
 -> human approval -> versioned registry -> router -> serving -> monitors -> rollback
```

Principles: the objective and the held-out data are outside the optimizer's writable surface; the validator is a separate service and code path from the optimizer; every recall logs the resolved config and memory IDs so outcomes can be attributed; the learning controller has hard compute and write budgets; and each actuator's output is a versioned, diffable, revertible artifact. These principles follow the failure modes in the notes: judge-keyword gaming, cached-answer-key reads in unsandboxed runs and holdout exploitation ([arXiv 2609.02246](https://arxiv.org/pdf/2609.02246)), a 57.1% reward-hacking rate with repeated holdout querying in BAITBENCH (snippet, verify) ([ACL Anthology](https://aclanthology.org/2026.findings-emnlp.2477.pdf)), and the poisoning results in section 6.

### Retrieval scoring with recency, salience, confidence and learned utility

Retrieval should be a calibrated score, not a cosine threshold. A defensible form follows the recency, importance and relevance decomposition of generative-agent memory ([Park et al., arXiv 2304.03442](https://arxiv.org/abs/2304.03442); a standard reference, not from the notes), extended with confidence, trust and outcome utility:

```
s(m | q, t) = w1·sim(q,m) + w2·lex(q,m) + w3·exp(-(t - t_m)/τ_k(m)) + w4·sal_m + w5·c_m + w6·û_m
              subject to: valid_from_m <= t < valid_to_m,  tenant/ACL(m) permits q,  trust(m) >= θ_k
```

Here `sim` is the cosine of pinned-model embeddings, `lex` a BM25-style lexical score, `τ_k` a decay constant per memory kind (guardrails very long, session notes short), `sal_m` an importance score assigned at write time, `c_m` calibrated write-time confidence, and `û_m` a lower confidence bound on outcome utility. For utility, let `h_m` be the number of times memory `m` was recalled, used and followed by an accepted outcome, and `n_m` the number of times it was recalled and used; then `u_m ~ Beta(a0 + h_m, b0 + n_m - h_m)` and `û_m` is a low quantile (for example 0.2) of that posterior, which keeps cold memories from being ranked by a lucky single success. The weights `w` are fitted by logistic or pairwise ranking on logged outcomes, then frozen and versioned per use case. Scope precedence stays as the existing deterministic arbitration (ORG > TEAM > AGENT > USER for guardrails, the reverse for preferences), applied after scoring. Attribution is the hard part: crediting a memory requires a logged recall plus evidence that the answer used it plus a trustworthy outcome signal, and the notes found no peer-reviewed study of credit assignment from implicit feedback in deployed assistants. The notes' evidence on lifecycle also constrains the update rule: prefer append-with-supersession (`valid_from`, `valid_to`, `superseded_by`) over LLM overwrite, because Mem0 abandoned overwriting after it erased context and ACE's "context collapse" shows iterative rewrites erode detail.

### Write gate and consolidation metrics

A belief is promoted from quarantine only if it passes an explicit predicate, replacing today's near-trivial lexical check:

```
promote(b) = [ #distinct_authenticated_principals(b) >= k ]  AND  [ conf(b) >= 0.85 ]
          AND [ entail(evidence, b) >= τ_e ]  AND  [ no contradiction with active memory, or supersession logged ]
          AND [ source trust >= θ ]  AND  [ human approval if scope in {ORG, TEAM} or kind = guardrail ]
```

Consolidation quality should be measured, not asserted. Useful quantities per consolidation run: precision of promoted beliefs against a labelled set, the rate of promoted beliefs later superseded or contradicted (a staleness/error proxy), recall of ground-truth facts after consolidation versus before (information loss), tokens per answered question, and the memory-count growth rate against a bounded budget. TraceRetain-style bounded retention supports capping store size with eviction by contribution rather than insertion order ([arXiv 2606.29178](https://arxiv.org/pdf/2606.29178)).

A research-grade write rule worth keeping in view is the Titans surprise-gated memory, which treats "surprise" as the gradient of an associative-memory loss and decays old content; as summarized in the notes (to be checked against the PDF) it has the form `S_t = η_t S_{t-1} - θ_t ∇ℓ(M_{t-1}; x_t)`, `M_t = (1 - α_t) M_{t-1} + S_t`, a momentum write with weight decay as the forgetting term ([arXiv 2501.00663](https://arxiv.org/abs/2501.00663)). An external-memory analogue (write only observations the current memory predicts poorly, decay unused items) is a cheap L1 heuristic that Everstate could test, but it is an inference, not a replicated result.

### Parametric adaptation: LoRA, SFT, preference optimization, RL

The LoRA update freezes the base weight `W0` and learns a low-rank delta:

```
W = W0 + (α / r) · B A,      B ∈ R^{d_out × r}, A ∈ R^{r × d_in},  r << min(d_in, d_out)
trainable params per adapted matrix = r (d_in + d_out)
```

([LoRA, arXiv 2106.09685](https://arxiv.org/abs/2106.09685)). Thinking Machines' study uses this parameterization with α = 32 and notes that the 1/r factor makes the optimal learning rate roughly independent of rank, with the best LoRA learning rate about 10x the full-fine-tuning rate, attention-only LoRA clearly underperforming MLP targets, and LoRA tolerating large batches less well ([LoRA Without Regret](https://thinkingmachines.ai/blog/lora/)). Derived from Llama-3.1-8B dimensions (32 layers, hidden 4096, MLP 14336, KV dim 1024, from the public config, unverified in the notes): rank 16 on all linear layers is about **41.9M** parameters (about 84 MB in bf16), and attention-only is about 13.6M (about 27 MB). QLoRA keeps a 4-bit NF4 base to fine-tune a 65B model on one 48 GB GPU ([arXiv 2305.14314](https://arxiv.org/abs/2305.14314)).

SFT minimizes `L_SFT = -E_{(x,y)} Σ_t log π_θ(y_t | x, y_<t)`. DPO (standard form from the original paper, not re-verified in the notes) optimizes preference pairs `(x, y_w, y_l)` against a frozen reference `π_ref`:

```
L_DPO = - E [ log σ( β [ log(π_θ(y_w|x)/π_ref(y_w|x)) - log(π_θ(y_l|x)/π_ref(y_l|x)) ] ) ]
```

([DPO, arXiv 2305.18290](https://arxiv.org/abs/2305.18290)). GRPO replaces a learned critic with a group-relative baseline, `A_i = (r_i - mean(r_1..r_G)) / std(r_1..r_G)` for `G` sampled completions, inside a clipped, KL-regularized PPO-style objective ([DeepSeekMath, arXiv 2402.03300](https://arxiv.org/abs/2402.03300); form not verified in the notes). The notes found no settled ranking among DPO variants: a 2026 controlled study of 20 variants stresses that algorithm papers use different bases, datasets and evals ([arXiv 2603.19335](https://arxiv.org/html/2603.19335), search summary). The recommended default is therefore the cheapest method matching the data: SFT where accepted exemplars exist, DPO where accept/reject pairs from corrections exist, and RL only where a deterministic verifier is available. To bound forgetting, add a drift anchor on replay and general data:

```
L_total = L_task + λ · KL( π_θ || π_0 ) evaluated on  D_replay ∪ D_general ∪ D_safety
```

which reflects RL's Razor (forgetting tracks KL shift) and the CPO critique (measure the KL on *prior-task* distributions, not only current-task data). For multiple adapters within one tenant, O-LoRA adds an orthogonality penalty on the A matrices, `λ_o Σ_{i<j} ||A_i^T A_j||_F^2`, so new subspaces avoid earlier ones.

### Forgetting, backward transfer and promotion as statistical tests

Let `R_{k,i}` be the score on evaluation suite `i` after the `k`-th adaptation cycle over `T` suites. The standard continual-learning metrics are (textbook forms from [Lopez-Paz and Ranzato, arXiv 1706.08840](https://arxiv.org/abs/1706.08840) and [Chaudhry et al., arXiv 1801.10112](https://arxiv.org/abs/1801.10112); the notes did not verify exact formulas):

```
BWT = 1/(T-1) Σ_{i<T} ( R_{T,i} - R_{i,i} )          (negative = forgetting)
F_i^k = max_{l<k} R_{l,i} - R_{k,i}                   (forgetting of suite i after cycle k)
FWT = 1/(T-1) Σ_{i>1} ( R_{i-1,i} - R_{base,i} )      (zero-shot gain on not-yet-trained suites)
```

For the adapter lifecycle the practical suites are the target-task suite, a general-capability suite, a safety/refusal suite and a memory-use suite (the adapter must not ignore retrieved facts), so BWT is reported separately for each. The Elastic Weight Consolidation penalty `Σ_i (F_i/2)(θ_i - θ*_i)^2` ([Kirkpatrick et al., arXiv 1612.00796](https://arxiv.org/abs/1612.00796)) is the textbook regularizer, but the notes retrieved no quantitative EWC-on-LLM evidence, so it is a research option, not a recommendation. The simplest forgetting protection is structural: train each adapter from the base on a ledger of curated data plus replay (retrain-from-ledger), rather than stacking sequential updates, which removes sequential adapter-to-adapter forgetting and also makes deletion tractable (section 6).

Promotion of any candidate (a memory policy, a config, a playbook or an adapter) should be a pre-registered statistical decision. Let `Δ_target` be the mean paired difference (candidate minus incumbent) on the held-out target suite, computed over sessions (cases within a session are correlated, so resample sessions with a cluster bootstrap, `B ≥ 10,000`). Promote iff all hold:

```
(1) LCB_{1-α/m}(Δ_target) >= δ_min                      (practically meaningful gain, Holm-corrected over m candidates)
(2) for every guard suite g:  LCB(Δ_g) >= -ε_g           (non-inferiority on general capability, memory-use, latency)
(3) safety suite: zero new canary failures, and UCB of failure-rate increase <= ε_s
(4) cost/latency within budget;  (5) human approval recorded
```

Select on a validation split and confirm on an untouched test split with a query budget, because max-over-candidates selection is biased upward (the winner's curse the audit identified in `alpha_evolve.py:678-683`). For binary pass/fail on paired cases, a rough sample size is `n ≈ (z_{1-α/2} + z_{1-β})² · p_d / Δ²`, where `p_d` is the fraction of discordant pairs; with `p_d = 0.2`, `Δ = 0.05`, `α = 0.05` two-sided and power 0.8, `n ≈ (1.96 + 0.84)² · 0.2 / 0.0025 ≈ 630` paired cases [derived; standard McNemar-style approximation]. The point of the example is that detecting a 5-point gain needs hundreds of held-out cases, and the current four-case suite cannot support any promotion decision.

### Routing and versioning

Routing should be deterministic first: resolve `(tenant, app, task family)` to a pinned adapter version via a registry, and fall back to the base model plus L1/L2 context when no adapter exists or its health check fails. A learned router is a later optimization (RouteLLM-style learned routers cut cost over 2x with minimal quality loss between strong and weak models on public data, per the project page; not checked against the paper) ([arXiv 2406.18665](https://arxiv.org/html/2406.18665v3)). Adapter merging (`ΔW = Σ λ_i B_i A_i`, TIES, DARE) should not be relied on: the evidence is mixed, and one benchmark finds merging mostly fails on LLMs. Each registry entry stores the base model ID and hash, adapter hash, training-ledger hash, hyperparameters, eval report, approver and rollback target; serving supports same-name in-place reload (vLLM) and LRU or pinned slots (SGLang), which makes version swap and rollback operationally cheap.

### Open questions for this section
Weights `w`, decay constants and promotion thresholds are design parameters with no empirical values from the notes; they must be fitted in experiments. Attribution quality for implicit outcomes is untested. DPO and GRPO equations are textbook forms not verified in the notes.

## 5. Feasibility of automated use-case-specific fine-tuning

### Feasible on open weights, bounded on cost, gated on science

Technically, automated per-use-case adaptation is feasible today. LoRA is cheap in parameters, QLoRA makes large bases trainable on one GPU, managed training exists, and multi-adapter serving is mature in open-source stacks. Training cost is small relative to everything around it. On Thinking Machines' Tinker, Qwen3-8B training is $0.44 per 1M tokens (as of 19 Oct 2026) ([Tinker pricing](https://thinkingmachines.ai/tinker/pricing/)), so 10M dataset tokens for 3 epochs (30M train tokens) costs about **$13.20**, and about $10.20 at Together's secondary-reported 8-9B SFT rate of $0.34 per 1M ([Together](https://together.ai/blog/together-ai-expands-fine-tuning-service-with-more-models-live-metrics-and-finer-controls); undated extract) [derived]. A self-hosted illustration is about 4.2 H100-hours (at an assumed, unmeasured 2,000 tokens/s) or roughly $11 to $17 at $2.64 to $3.92 per hour ([Spheron](https://www.spheron.network/blog/h100-price-per-hour-2026/); [AIMultiple](https://aimultiple.com/gpu-index)) [derived, throughput assumption must be measured]. The expensive parts are data curation, evaluation compute, human review and recurring serving, not the gradient steps.

The hard parts are scientific. Whether an adapter *helps*, *does not hurt elsewhere* and *does not leak* has to be established per release with held-out suites, and the notes record two relevant warnings: benign fine-tuning can erode safety alignment (10 adversarial examples jailbroke GPT-3.5 Turbo for under $0.20; benign data also degraded safety to a lesser extent) ([Qi et al., arXiv 2310.03693](https://arxiv.org/abs/2310.03693)), and teaching new facts by fine-tuning backfires (Gekhman). "Automated" should therefore mean automated proposal, training and validation, with human-approved promotion.

### What "automatic" should cover, step by step

**Data curation.** The notes retrieved nothing on training-data selection, dedup, drift detection, active learning or adapter registries, so this pipeline is an inference from the surrounding evidence. Candidate examples come from three kinds of traces: explicit user corrections, accepted outputs with a deterministic verifier pass (schema valid, tool call succeeded, test passed), and human-approved exemplars. Each candidate carries provenance and tenant tags and is excluded if it fails any of these filters: PII and secret scrub, poisoning screen (trust level below threshold, or written through a quarantined channel), "fact-only" content that belongs in memory (Gekhman: do not teach facts when retrieval will do), near-duplicates (exact plus embedding-based), and examples where the base already succeeds (low marginal value). Splits are by session and time, never by random row, with the test split frozen and its query count budgeted. Everything lands in an append-only, hash-chained **training ledger** so a deletion request can rebuild the adapter from the ledger minus the deleted records.

**Learning triggers.** A trigger should fire on evidence, not schedule alone. Proposed triggers, all to be calibrated in experiments: (a) a stable, repeated failure class (for example the same tool-schema error or format violation above a rate threshold with a confidence bound) that L1/L2 fixes have not removed after a trial period; (b) a token or latency cost where a long stable playbook or few-shot prefix is attached to more than N calls per month and distillation would remove it; (c) enough curated examples to exceed a minimum for the task (LoRA matches full fine-tuning on small-to-medium datasets but underperforms past its capacity); (d) a verified-reward environment (tests, validators) enabling RL; (e) drift on an online monitor (success rate of the deployed version dropping below a bound). Triggers open a *candidate* job, not a promotion. Each trigger carries a per-tenant monthly compute cap and a per-cycle cap on candidates (each extra candidate raises the multiple-comparison burden).

**Sandboxed experimentation with fixed objectives.** The notes' governance evidence says the optimizer must not control its evaluator: objectives and held-out data sit in a service the training job cannot write, the job runs hermetically with no filesystem access to eval answers or caches, repeated holdout querying is budgeted, canary cases that should never pass are mixed in, deterministic checks gate LLM judges (AgentTrust found a judge gated on a deterministic rule floor was the best configuration), and an independent validation job (different code path, different judge model than the generator, to limit self-preference bias) produces the promotion report ([arXiv 2609.02246](https://arxiv.org/pdf/2609.02246); [AgentTrust, arXiv 2606.08539](https://arxiv.org/pdf/2606.08539)). No source combined sandbox, holdout, rollback and human promotion into one tested pattern, and none addressed compute-budget governance, so these controls are proposals to be validated by the dry-run in experiment E12.

**Human-approved promotion and rollback.** An approver sees a diff-style report: data composition, hyperparameters, target gain with interval, guard-suite non-inferiority, safety suite, cost, and a rollback target. Promotion is canary first (a small traffic share or shadow mode), with automatic rollback if monitors cross pre-set bounds. Rollback is a pointer swap in the registry plus in-place adapter reload, which the serving docs support.

### Serving, GPU and latency envelope

The serving envelope in the notes is mostly design parameters, not independent benchmarks. vLLM exposes `--max-loras`, `--max-cpu-loras` and `--max-lora-rank`, and warns that runtime LoRA updating is a security risk in untrusted environments; SGLang defaults to 8 adapter slots per batch with LRU or FIFO CPU eviction and reports a 20 to 80% latency gain from its `csgmv` kernel at high concurrency and about 35% lower median time-to-first-token from overlap loading (its own docs, conditions unstated). Punica reports about 2 ms per-token overhead and 12x throughput versus baselines on a fixed cluster (abstract only); S-LoRA reports up to 4x throughput over naive LoRA serving and thousands of adapters (abstract; one PDF rendering says 30x, so treat 4x as the cited figure). Vendor claims of about 200 ms adapter load and "upwards of 100" or "hundreds" of adapters per GPU (LoRAX, Fireworks) are unreplicated, and a TrueFoundry experiment found latency rising with adapter count while a later summary said stable. A planning bound is memory arithmetic: 1,000 rank-16 adapters at 84 MB is about 84 GB in the host tier, with only the active few on GPU [derived]. Frozen base weights for an 8B model are about 16 GB in bf16 or 5 to 6 GB in 4-bit; full fine-tuning of 8B with Adam needs roughly 128 GB before activations (standard estimate, not sourced), which is why LoRA is the default. All GPU price points are aggregator stamps, not provider lists.

### What would make this infeasible

It becomes infeasible, or not worth it, when the customer's workload runs on a closed model that cannot be tuned, when call volume is too low for a behavioral adapter to amortize its evaluation and serving cost, when the failure class is factual (retrieval fixes it), when no deterministic or well-calibrated outcome signal exists to validate against, or when data residency forbids sending traces to the training environment. The first of these is the largest for an ADK-and-Gemini platform.

### Open questions for this section
Measured LoRA GPU-hours for 7B to 70B, measured multi-adapter throughput under tenant churn, current official 2026 prices (Vertex Gemini tuning, OpenAI SFT/DPO, Together, Fireworks), data-selection and drift-detection methods, and canary/shadow patterns for memory or prompt changes were not established in the notes.

## 6. Privacy, tenant isolation, safety and catastrophic-forgetting considerations

### Memory is an attack surface, and Everstate has reproduced the attack

The 2026 literature treats a memory write as untrusted input with long-lived effect. A taxonomy of memory poisoning finds a single adversarial write can alter long-term behavior, more aggressive write and retrieval policies are more exploitable, and existing prompt-injection defenses do not cover it ([Dash et al., arXiv 2606.04329](https://arxiv.org/abs/2606.04329); a 50.46% attack success figure in a search summary is unverified). MINJA reports 98.2% injection success and 76.8% attack success with query-only access (idealized conditions; a later evaluation questions realism, snippets) ([arXiv 2503.03704](https://arxiv.org/html/2503.03704v5)), and AgentPoison exceeds 80% attack success with under 1% benign degradation at a poison rate under 0.1% ([arXiv 2407.12784](https://arxiv.org/abs/2407.12784)). OWASP LLM08:2025 names cross-context leakage in multi-tenant vector stores, embedding inversion and poisoning, and prescribes permission enforcement at retrieval time, per-tenant indexes or namespaces, source-ACL propagation into embedding metadata and immutable retrieval logs ([OWASP](https://genai.owasp.org/llmrisk/llm082025-vector-and-embedding-weaknesses/)). Against this, section 1 shows that two authorized API calls plus a dream trigger created an ORG-scoped TLS-disable guardrail, personal memory is a shared bucket, the MCP write tools carry no authorization, and no rate or size limits exist. A learning loop that consumes this memory would amplify, not correct, those defects. The ordering rule follows: **identity, tenancy, write gating and quarantine come before any learning feature.**

The defense set proposed (inference from the cited work, not a tested combination): provenance on every item (source, tenant, time, authenticated writer); authenticated, server-assigned session identity so one principal cannot self-attest independence; a quarantine tier where new memories are not retrievable until an automated screen and, for high-impact kinds, sampled human review pass; retrieval-time ACL filtering rather than post-filtering; trust scores that cap how much any single source can influence context; and TTL plus versioned supersession for stale beliefs. The costs are real: gating adds latency and reviewer labor, quarantine delays freshness and trades against "aggressive write" behavior, and trust-weighting can suppress legitimate low-provenance facts. No source quantified false-positive cost of quarantine, or stale-belief retrieval rates in enterprise memory systems.

### Tenant isolation patterns

For L1, isolate by server-bound scope (derived from identity, never from the request body), per-tenant namespaces or indexes, and ACL metadata checked on every search. For L3, one adapter per tenant (or per app) is the weight-level isolation boundary, but it does not stop retrieval-level leakage, and shared base-model serving has its own side channels: prefix and KV-cache timing leaks are documented for multi-tenant serving (snippets: [CacheSolidarity, arXiv 2603.10726](https://arxiv.org/html/2603.10726v1); [survey, arXiv 2610.33475](https://arxiv.org/pdf/2610.33475)), and no LoRA-specific side-channel analysis was found. Disabling cross-tenant prefix caching costs inference spend, while per-tenant indexes cost index overhead and reduce cross-tenant shared learning. Adapter files should be treated like code: signed, hash-pinned, with training-data provenance, loaded only through authenticated admin paths (vLLM flags runtime LoRA updating as a risk, SGLang gates admin endpoints with a key). Per-tenant encryption keys (CMEK), row-level security and residency were not covered by any 2026 source retrieved.

### Deletion and the right to be forgotten

Deleting from a memory store is tractable; deleting from weights is not. TOFU's main result was that none of the baseline unlearning methods were effective ([arXiv 2401.06121](https://arxiv.org/abs/2401.06121)); OpenUnlearning notes TOFU reuses training questions and can inflate metrics ([arXiv 2506.12618](https://arxiv.org/html/2506.12618v2), snippet); no consolidated 2026 leaderboard or adversarial re-elicitation study was found. The design consequence is firm. Personal data stays out of shared and per-tenant weights unless necessary, hard-deletes with tombstones from memory planes, and deletion of anything that entered an adapter is handled by rebuilding the adapter from the training ledger minus the deleted records, so the deletion SLA equals adapter rebuild time. Today's deletion is only partial: per-record and scope delete exist (`server.py:2687-2702`, `spanner_client.py:1182-1300`), but BigQuery `agent_logs`, `episodes_log` and `scoped_memories_replica` rows, `studio::` blobs, `session_summaries` and in-process caches are not covered (section 1). Backups, derived embeddings and logs remain unaddressed by any source. On regulation, the EU AI Act high-risk deadline was reported moved from 2026-08-02 to 2027-12-02 under the Digital Omnibus, with one internally inconsistent secondary source (DLA Piper) describing adoption and entry into force on 2026-07-27 and another reporting different dates for machine-readable marking; treat all of it as **unverified until checked on EUR-Lex** ([DLA Piper](https://knowledge.dlapiper.com/dlapiperknowledge/globalemploymentlatestdevelopments/2026/The-Digital-AI-Omnibus-Proposed-deferral-of-high-risk-AI-obligations-under-the-AI-Act); [OneTrust](https://www.onetrust.com/blog/eu-digital-omnibus-proposes-delay-of-ai-compliance-deadlines/)). GDPR erasure, DPIA duties, CCPA/CPRA, HIPAA, SOC 2 and ISO/IEC 42001 requirements were not researched. Supermemory lists SOC 2 and HIPAA on its pricing page (vendor claim); Everstate has no PII scrubbing and UI-only redaction labels, so it cannot currently make equivalent claims.

### Catastrophic forgetting as a safety issue

Benign adaptation can erode refusal behavior, so safety is a forgetting target, not only a capability. Each adapter release must rerun a fixed refusal and harmful-prompt regression suite and a general-capability suite, with BWT reported per suite and a zero-tolerance rule on canary safety failures; the cost is eval compute per release and a reviewer loop for failures. For L1 and L2 the analogue is memory-induced behavior drift: OWASP notes retrieval can alter behavior (for example reduced empathy while factually improved), and benign accumulation raised violation rates in the 2026 study cited in section 2, so the same regression suite should run after large memory or playbook changes. Structural protections, in order of simplicity: retrain from ledger rather than stacking sequential updates; LoRA with MLP targets and a KL anchor on replay and safety data; on-policy data where possible (with the CPO caveat); per-task orthogonal adapters if one tenant needs several; and no reliance on merging or on EWC without evidence. Monitoring methods with measured false-alarm rates for continual safety drift were not found.

### Open questions for this section
Memorization and extraction risk for per-tenant LoRA versus full fine-tuning, DP-LoRA utility cost, membership-inference results for adapters, PoisonedRAG results, defense false-positive rates, and the status of the EU omnibus are open.

## 7. Reproducible experiments, benchmarks and ablation studies

### Ground rules

Experiments are ordered so that measurement is fixed first, because every later claim depends on an evaluator that can fail. Each experiment below should have a pre-registered hypothesis, acceptance threshold and analysis plan committed before running; the thresholds shown are **proposed starting points to be calibrated**, not values from the notes. Results are reported with confidence intervals (session-level cluster bootstrap), multiple seeds where training is involved, and the full configuration.

**Model-call routing.** All LLM calls made for experiments, evals and judges go through the user's local OpenAI-compatible endpoint at `http://127.0.0.1:18080/v1` (models such as `gpt-6.2-sol` and `gpt-6-luna`), with the exact model ID pinned and recorded in every results file, along with temperature, seed (if supported) and prompt hash. The endpoint does not support embeddings, so embedding experiments need a separately pinned embedding source (a local open-weight embedder for offline work, or the production Vertex embedding path measured on its own) recorded the same way. The production Gemini and Vertex paths remain unchanged. Judge and generator should be different models where possible (LLM judges show position, verbosity and self-preference biases), and every judge is validated against a human-labelled subset before use, including an adversarial wrong-answer set, in light of the LoCoMo judge's 62.81% false-accept rate and the 80%-to-51.9% calibration collapse in 2609.02246. Adapter-training experiments (E9 onward) need GPU access and an open-weight base, which the local endpoint does not provide; they run in a separate training environment, with the local endpoint used only for judging and data synthesis.

## 8. Cost analysis and dependency-aware production roadmap

### Unit economics

**Competitor price anchors (list prices, as read).** Supermemory charges $0.005 per 1K memory tokens for plain content ($0.010 rich), so about $5 per 1M ingested tokens, plus $0.005 per 1K search queries; Pro is $19/month and Scale $399/month ([pricing](https://supermemory.ai/pricing)). Zep charges one credit per 350-byte episode with retrieval and storage at zero credits; Flex is $125/month for 50,000 credits with $25 per 10,000 overage ([pricing](https://www.getzep.com/pricing)), which works out to about $0.0025 per credit or roughly $7.50 per MiB of ingested episodes [derived]. Mem0's free tier is 10,000 adds and 1,000 retrievals per month and its paid rates are not public ([pricing](https://mem0.ai/pricing)). Google Memory Bank is reported at $0.25 per 1,000 memories or events by a third-party guide (unverified) ([Google docs](https://cloud.google.com/vertex-ai/generative-ai/docs/agent-engine/memory-bank/overview?hl=en)). No vendor publishes cost per monthly active user. Everstate's own cost drivers (Spanner processing units, BigQuery, Cloud Run, Vertex calls) were not priced in the notes, so its gross margin against these anchors is an open item.

**Cost of the learning loop itself.** Evaluation and judging dominate L1 and L2 learning cost. A cycle's cost is approximately `N_cases × calls_per_case × tokens_per_call × price_per_token` for candidates plus the same for baselines, multiplied by seeds and by the number of candidates `m`. Because multiple-comparison control makes each extra candidate more expensive to confirm, the budget should cap `m` and prefer fewer, better-motivated candidates (GEPA's rollout efficiency is the reference point, with the caveat that its 35x figure is a rollout count). Exact dollar costs depend on judge-model prices not in the notes.

**Cost of a parametric tier.** Training is cheap: about $13 for 30M tokens on Qwen3-8B at Tinker's rate, or under $20 self-hosted on one H100 under stated assumptions (section 5) [derived]. RL via managed APIs is billed differently: OpenAI RFT is $100 per wall-clock training hour for o4-mini (rollouts, grading and weight updates billable; model-based grader tokens extra) ([OpenAI](https://help.openai.com/en/articles/11323177-billing-guide-for-the-reinforcement-fine-tuning-api)), but that platform is being wound down for new users. Serving is the recurring cost. Per-million-token serving cost is `GPU $/hr ÷ (tokens/s × 3600) × 10^6`; at $3.92 per hour (AIMultiple median) and an assumed 2,000 tokens/s aggregate, that is about **$0.54 per 1M tokens** [derived; throughput assumed, unmeasured]. A dedicated H100 at $3.92 per hour is about $2,860 per month (730 hours) [derived], so adapter hosting only beats per-tenant dedicated GPUs when many tenants share the base; Fireworks reports serving LoRAs at base-model rates ($0.20 per 1M for Llama 3.1 8B, vendor claim) ([Fireworks](https://fireworks.ai/blog/multi-lora-serving)), which suggests external multi-LoRA hosting is a cheaper entry than building Everstate's own serving. The break-even for an adapter that removes a long stable prefix is `calls_per_month × prefix_tokens × input_price` (tokens saved) against `training + evaluation + review + added serving overhead`, and the savings only matter relative to the incumbent model's price: replacing a Gemini prompt prefix with a self-hosted 8B adapter changes the base model too, so quality must be re-validated (E9). Storage is negligible (about $0.008 per month for an 84 MB checkpoint at $0.10 per GB-month) [derived]. The dominant costs of a parametric tier are therefore the ledger, the validator, human review, safety suites and the always-on serving path, not training.

**Unit-economics conclusion.** An L1+L2 learning loop is mostly a software and evaluation-compute cost with no new GPU fleet. A parametric tier adds fixed serving cost and a per-tenant curation and review cost that only amortizes for tenants with high call volume on a stable, verifiable behavior. Pricing should therefore meter the loop's measurable outputs (validated improvements promoted, evaluation compute consumed) and offer the adapter tier as a premium add-on to qualified tenants.

### Dependency-ordered roadmap

Nothing below should be implemented blindly. Each phase begins with a spike that confirms the audit's findings in the live environment (the audit was static plus offline probes) and a pre-registered experiment from section 7; a phase ships only when its exit criteria are met, and no change in this roadmap is already done. Proposals are conditional on those results.

| Phase | Scope | Depends on | Exit criteria |

Parallelism is possible within phases (for example P2 telemetry with P1 hardening) but not across the dependency arrows. The most important sequencing rule is that P5 is conditioned on evidence from P3 and P4: if memory and agent-level learning close most of the gap, the parametric tier may not be worth building.

### Open questions and evidence gaps (consolidated)

The reference architecture (`davenportjw/agentic-memory`) was not audited. No live-system measurements exist; all codebase findings are static or offline-probe results. Most 2026 research items are preprints read via summaries or snippets, and several (SLEEP's objective and compute, Titans' exact equations, SR-TTT, Mela, MemoPilot, CapTrack, BAITBENCH figures, MPBench's attack rate) need primary-text checks. Independent replications of ACE, GEPA, ReasoningBank, Memento, and every vendor benchmark are missing. Evidence on credit assignment from implicit feedback, decay and reconsolidation schedules, training-data selection and drift detection, canary and shadow patterns for memory changes, compute-budget governance for optimizers, adapter side channels, per-tenant LoRA memorization and DP-LoRA cost, and measured adapters per GPU and LoRA GPU-hours was not found. Current official 2026 prices for Vertex Gemini tuning, OpenAI SFT, Together, Fireworks and Google Memory Bank are unverified; GPU prices come from aggregators. EU AI Act dates are unverified; GDPR, HIPAA, SOC 2 and ISO 42001 duties were not researched. Whether any Everstate customers require weight-level adaptation, and what they would pay for it, is unknown. The right posture is to treat the recommendation as a hypothesis to be disproved by P0 to P4, not as a plan to execute.
